## 目标

下一阶段不继续横向堆功能，而是按以下因果顺序推进：

1. 先把已经通过完整门禁的仓库加固改动形成可恢复、可审阅的交付检查点；
2. 再降低“小玩意”页未开始游玩时的脚本成本，并保持现有 11 项功能和无 JavaScript 结构不变；
3. 用自动化审计确认页面密度、交互重复与真实维护成本，只抽取已经出现且语义一致的共同机制；
4. 原拟制作一个“接通电路”隔离原型；用户在 M2 验收后否决该方向，因此不执行。

本计划不是对当前加固分支的继续堆叠。完成第一阶段交付后，新功能应从更新后的正式主分支创建新的仓库外 worktree。

## 阶段 1：小玩意脚本按首次展开加载

### 设计

保留完整服务端渲染的 11 项 HTML，只改变本地 JavaScript 的请求时机。增加一个很小的页面级加载器，让每个 `details` 声明其本地脚本依赖；首次展开、URL hash 直接打开或程序化打开时，按顺序加载对应脚本。脚本 URL 必须由 Liquid 在构建期从固定映射生成，加载器不接受 hash、查询参数、外部响应或任意 DOM 字符串作为脚本来源。相同共享脚本以 Promise 缓存，只请求、执行一次。

建议依赖边界：

- 萌娘百科：`moegirl-quiz.js`；
- 名画：`art-glimpse.js`；
- AniList：关系逻辑与界面两个脚本；
- 色差：安全随机与色差脚本；
- 盲估十秒／反应时间：安全随机、共用历史与挑战脚本；
- 数字 Wordle、凑成 24、翻灯：安全随机与各自脚本；
- 两个生成器：安全随机与生成器脚本。

加载器负责同源白名单、依赖顺序、重复展开、并发展开、部分依赖成功后的失败状态和显式重试，不负责游戏内部状态。失败的 Promise 可以重建，已经成功执行的共享依赖不得重复执行。现有游戏算法和 DOM 契约尽量不改；若某脚本只支持 `DOMContentLoaded` 初始化，则只补充“文档已经就绪时也可初始化”的小边界，不借机重构内部实现。

### 验收

- 所有项目收起时，小玩意加载器／展开辅助脚本的未压缩构建产物不超过 4 KiB；连同现有站点基础脚本，HTML 初始引用的同源 JavaScript 未压缩文件总量不超过 15 KiB。该口径用于获得确定性基线，不冒充实际压缩传输量；构建产物契约检查字节和静态引用，真实 Chromium 另检查冷缓存请求集合。
- 首次展开只请求该项目所需的同源脚本；再次展开不重复请求。先后展开共享依赖的项目时，共享脚本只执行一次。
- URL hash 直达、浏览器前进／后退、键盘展开和脚本加载失败后的显式重试均可用，并具有可读状态。
- 展开外部数据游戏只加载本站脚本，不请求外部服务；仍须在玩家明确点击开始后才允许现有单局请求。
- 无 JavaScript 时，完整标题、说明、隐私／许可边界和不可用提示仍然存在；不把主要内容改成客户端模板。
- 现有 Python、Node 和 163 项浏览器契约保持通过，并增加“初始请求集、按需请求集、一次性初始化、失败恢复”回归。

## 阶段 2：页面密度与重复机制审计

### 自动过滤

1. 在 320、390、1280 px，中文／英文，明亮／夜晚和 reduced-motion 下遍历 11 项；检查横向溢出、焦点恢复、状态播报、触控目标和连续展开多个项目后的滚动行为。
2. 记录每项首次展开的本地请求数、脚本字节、初始化时间和外部请求数；外部服务测试继续使用固定桩，实时探针单独显式运行。
3. 对设置应用／重置、开始新局、撤销、显示答案、网格方向键和随机失败等行为做结构比对。只有语义、错误处理和生命周期都一致的重复，才列为抽取候选。
4. 不因为文件行数大而拆分代码；优先处理会减少首始载荷、重复 bug 或测试矩阵的边界。

### 人工判断材料

自动问题清零后，再生成一个单文件 HTML 审阅稿，包含中英文页面全景、11 项分组密度、典型项目展开后的截图、请求体积对比和仅剩的主观问题。用户只需要判断：

- 四个分组和当前排序是否仍便于寻找；
- 同时允许多个项目展开是否仍符合预期；
- 是否需要在进入第 12 项前调整标题／简介密度。

已明确的隐私、双语、键盘和“不强制关闭其它项目”要求不重复交给用户判断。

### 验收

- 自动缺陷先修复，人工审阅只保留产品偏好问题。
- 若没有两个以上真正同构的重复，不创建共享框架，并在审计结论中明确记录“不抽取”。
- 审阅稿本身不进入正式生产树；最终决策和必要事实更新进项目记忆。

## 阶段 3：唯一候选——“接通电路”隔离原型（已取消）

本节仅保留为历史方案，不构成待办。用户判断该玩法过于传统，缺少额外逻辑新意与实际站点价值，因此不得实现，也不得自动改做其它传统候选。

### 选择理由

“接通电路”在既有路线中优先级最高，能复用翻灯已经验证的网格焦点和键盘经验，但核心循环由“翻转邻格”变为“旋转局部端口并理解整体连通”，新增的是网络规划而非另一种反应、计时或颜色挑战。相比之下，“漫水”仍需解决颜色冗余和步数基准，“节奏复现”与现有计时挑战重叠且有音频启动、输入延迟和无声替代风险。

### 原型范围

- 先只做固定尺寸、固定规则的标准局，不添加难度名称、计时、分数、锁定方块或持久化。
- 从覆盖网格的连通树构造目标端口，随机旋转方块；生成过程使用可注入随机源，生产仍只接受 `crypto.getRandomValues()`。
- 使用独立求解器统计解数量并在找到第二解时停止；只有恰好一个合法连通、无悬空端口的方向配置才可出题。
- 生成尝试次数必须有明确上限；失败显示可重试状态，不允许无界循环或用未经证明的固定样本伪装随机题池。
- 每格使用原生按钮；方向键移动焦点，Enter／空格旋转。视觉同时使用端口线、方向和状态，不以颜色独自表达；每格的无障碍名称包含行、列和当前端口方向。
- 原型位于独立功能分支／worktree。为试玩可以存在仅分支可见的实验页面，但在合并前必须二选一：正式集成，或删除页面与生产代码。
- 只参考传统规则和交互边界，不复制 Simon Tatham 或其它实现的代码、图形和具体关卡；若实际复用第三方内容，必须另做许可审计。

### 自动闸门

- 纯逻辑测试覆盖旋转、端口匹配、连通性、胜负判定、撤销／重置和随机源失败。
- 独立 Python oracle 对确定性种子批次复核“生成题可解且唯一”，并确认求解搜索和生成尝试有界。
- 浏览器回归覆盖中英文、320／390／1280 px、完整键盘通关、触控、明暗主题、reduced-motion、无 JavaScript和随机源不可用。
- 原型不发送网络请求，不新增 Cookie／存储键，也不破坏阶段 1 的首始脚本预算。
- 全量统一门禁通过后，才生成试玩审阅稿；审阅稿并列展示“接通电路”和“翻灯”的核心循环，供用户判断二者是否足够不同。

### GO／NO-GO

只有同时满足以下条件才进入正式索引：

1. 生成器与独立 oracle 对唯一解、可解性和有界性结论一致；
2. 小屏和完整键盘路径没有阻断；
3. 默认局无需先读设置即可开始，规则说明能在一个短段落内讲清；
4. 用户试玩确认它与翻灯具有足够不同的思考体验；
5. 加入后页面密度仍可接受，且首始脚本预算不回退。

历史方案曾规定核心条件不成立时转向“漫水”；2026-08-07 的用户决定已取代该安排，不制作“接通电路”，也不转向其它传统候选。
