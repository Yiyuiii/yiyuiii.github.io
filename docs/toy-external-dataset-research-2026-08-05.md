# 外部接口小游戏调研（2026-08-05）

## 用户边界

本调研服务于双语静态“小玩意”页。用户已经明确两条长期边界：

1. **不做需要 API 密钥的项目**：站点、维护者和读者都不申请或提供密钥；不在前端嵌入密钥，也不新增代签后端。
2. **不批量下载外部数据**：不生成、提交或向读者下发大型本地题池、馆藏索引、音频索引和媒体副本。只能在读者明确开始一局后，调用产生本局内容直接必需的官方公共接口或媒体地址。

运行时响应只保留在当前页面内存；不写 Cookie、`localStorage`、`sessionStorage` 或其它持久化存储，不静默续页、不预取下一局。若一次已披露的请求没有形成合格题目，应说明并允许读者主动重试。第三方请求前必须说明服务方能看到本次请求、来源页和 IP 地址。

“外部数据量大”只用来避免人工小白名单，不再通过下载数据转化为本站存储负担。题目质量必须在外部接口单次或少量直接响应的边界内解决。

## 修订后的候选排序

| 优先级 | 游戏 | 运行时接入 | 结论 |
| --- | --- | --- | --- |
| P0 | **百科条目猜猜的 Wikipedia 来源** | 开始后向当前语种 Wikipedia Action API 请求一次随机主命名空间批次 | 四个方向中最可行；作为现有游戏的来源选项，不新增同构折叠项 |
| P1 | **Bangumi 作品关系猜猜** | 开始后请求一次官方 API 批次，在内存中筛选作品、角色或改编关系 | 无密钥、中文题名自然；只用文字与关系，不用封面 |
| P1/P2 | **AniList 作品关系猜猜** | 每局一次公开 GraphQL 查询，不认证、不缓存下一局 | 技术可行，但中文题名、条款、稳定性和内容过滤弱于 Bangumi |
| P1/P2 | **AIC 名画一瞥** | 点击后实时请求 AIC 元数据及本局所需 IIIF 图片 | 许可清楚、视觉差异大；无本地索引后随机抽样和请求数量需要原型验证 |
| P2 | **MusicBrainz 音乐时间线** | 每局实时查询元数据，不取音频或封面 | 无密钥但缺少高质量随机入口，且每秒一次限制使多请求体验一般 |
| 排除 | **动画封面猜题** | AniList/Bangumi 封面地址 | 没有足够的逐图再利用证据 |
| 排除 | **主流听歌猜曲** | 商业试听或第三方音频 | 找不到同时无密钥且允许独立游戏娱乐的录音来源 |
| 排除 | **Wikidata 构建期时间线、Commons 本地音频索引** | 批量生成本地题池或媒体索引 | 违反“不批量下载数据”的最新边界 |
| 排除 | **Europeana、Spotify、Jamendo、Freesound 等密钥路线** | 需要项目密钥、凭据或代签 | 违反无密钥边界 |

## 允许的调用模型

### 单次题目批次

玩家点击“开始”后，请求一个足以在浏览器内筛选本题的小批次。响应只用于当前局；不追随 continuation，不因筛选失败而静默补请求。Wikipedia、萌娘百科、Bangumi 和 AniList 的文字题优先采用这一模型。

### 当前局的元数据与媒体

视觉题可以在玩家点击后请求本局元数据和本局实际展示的媒体，但不能先下载全馆索引或预取后续题目。入口应披露大致请求数量，例如“一次馆藏元数据请求和四张候选图”。AIC 适合这一模型。

### 不允许的变体

- 构建脚本抓取数千或数万条记录再提交 JSON；
- 为随机抽样先向读者下发完整 ID 列表；
- 下载并裁切一批图片或音频放进仓库；
- 在后台或折叠项尚未打开时预取题目；
- 本批次筛选失败后自动继续翻页，导致披露的请求数失真。

## AniList 详解

AniList 的公开 GraphQL 查询不需要密钥或登录。官方文档允许未认证客户端查询动画、漫画和角色，并能一次取得标题、简介、播出日期、原作类型、制作公司、角色关系、流行度、成人标记、封面 URL 与站内链接。

适合的文字循环包括：

- 给出一部动画和四名角色，找出不属于该作品的一名；
- 根据原作类型、年份、集数和制作公司猜作品；
- 判断前传、续作和外传关系；
- 找出四部动画中最早播出或唯一不同原作类型的一部。

它符合“不批量下载”的新架构：每局只提交一次 GraphQL 查询，取一个小批次，在页面内存中筛选，结束后丢弃。但仍有四个问题：

1. 官方禁止把 API 当备份或数据存储，也禁止 hoarding 与 mass collection；这与实时小批次一致，却不允许本地大题库。
2. 正常限额为每分钟 90 次，当前官方明确标为降级状态、限为每分钟 30 次；严重故障时可能暂停 API。
3. `MediaTitle` 只有罗马字、英语、原生语言和用户偏好字段，没有独立中文译名；未登录时用户偏好默认罗马字。
4. `coverImage` 只返回不同尺寸 URL，没有逐图再利用许可证。API 使用条款不能替代原作品或宣传图版权许可。

`isAdult=false` 也不是完整的内容过滤。AniList 官方说明其成人分类不保证符合其它平台标准，Ecchi 不被算作成人内容；仍需排除敏感或剧透标签。

结论：**仅保留文字和关系原型，不做 AniList 封面题。** 它无需密钥、也无需本地存储，但中文页面自然度和第三方实时稳定性使其低于 Bangumi。

官方证据：

- 无认证可读公开数据：<https://docs.anilist.co/guide/auth/>
- 禁止备份与批量囤积：<https://docs.anilist.co/guide/terms-of-use>
- 当前降级限流：<https://docs.anilist.co/guide/rate-limiting>
- 稳定性与成人内容边界：<https://docs.anilist.co/guide/considerations>
- 标题字段：<https://docs.anilist.co/reference/object/mediatitle>
- 作品和封面字段：<https://docs.anilist.co/reference/object/media>

## 动画封面猜题详解

理想循环是显示一张被裁切、模糊或逐步揭开的封面，再从四个标题中选择。它视觉直接，但当前不实施：

- Bangumi 官方版权页把封面列为用户提供的条目信息，同时明确已有版权作品按 fair use 处理并标来源。Bangumi 能在自身语境展示，不等于本站获得再利用或裁切许可。
- AniList 只返回封面 URL，没有逐图许可证，也没有在已核查的 API 条款中授权把封面用于独立猜谜娱乐。
- 热链只改变文件由谁提供；裁切、缩小、模糊或像素化仍然利用原图，不自动解决权利问题。
- 封面经常直接写出作品名，同系列不同季度、总集篇、剧场版和重制版又高度相似。即使许可解决，仍要处理文字泄漏、系列去重、成人内容和相似候选。

只有当无需密钥的官方接口为每张图片提供可核验的第三方展示与改编许可，并有可靠中英题名时才重启。届时也只在点击开始后请求本局一张题图和必要候选，不建立封面索引。

来源：<https://bgm.tv/about/copyright>、<https://docs.anilist.co/reference/object/mediacoverimage>

## 听歌猜曲详解

主流玩法需要播放 5–15 秒录音。元数据许可不能覆盖录音中的作曲、歌词、表演和录音制品权。

- MusicBrainz 无需密钥，核心元数据大多为 CC0，但官方明确说明它不存储也无法访问音乐录音，只能提供曲名、艺人、发行和关系数据。
- Apple iTunes Search API 虽然无需项目密钥并返回歌曲预览，但官方条款只允许预览用于推广对应商店内容，要求购买链接、徽章和署名，并禁止把预览用于脱离推广目的的独立娱乐。
- Spotify、Jamendo、Freesound 等常见路线需要凭据或密钥，直接排除。
- Wikimedia Commons 有自由许可音频，但没有适合本游戏的高质量随机音频接口。若不允许预先建立索引，实时从庞杂媒体中筛选会产生无关请求、延迟和流量，违背“只请求本局直接相关内容”的目的。

结论：**主流听歌猜曲和先前建议的 Commons 本地“听声猜猜”均退出候选。** 除非以后出现无需密钥、直接面向可复用音频游戏素材的官方接口，否则不继续。

官方证据：

- MusicBrainz 无录音边界：<https://musicbrainz.org/doc/About>
- MusicBrainz 数据许可：<https://musicbrainz.org/doc/About/Data_License>
- iTunes 预览使用限制：<https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/>
- Commons 音频许可复杂性：<https://commons.wikimedia.org/wiki/Commons:Audio/en>

## Wikipedia 导言题详解

这是当前最适合直接实施的外部接口路线。中文与英文 Wikipedia 使用同一套无密钥 MediaWiki API，中英文页面可请求各自语种，不再让英文页面只能显示中文题料。

建议把现有游戏升级为 **“百科条目猜猜”**，在开始前选择来源：

- 中文页保留萌娘百科为默认来源，可选中文 Wikipedia；
- 英文页默认 English Wikipedia，可选明确标为中文题料的 Moegirl；
- 来源、语种、请求次数、许可和隐私说明随选择变化。

一局只需一次 Action API 请求：用 `generator=random` 限定主命名空间，取最多 20 个随机页面，同时请求 HTML 导言、分类、`pageprops` 和修订 ID。导言中的 `<b>` 片段通常包含条目名与别名，可先替换为遮蔽块，再转成纯文字；作答后链接准确修订并注明 CC BY-SA 与“名称已遮蔽”。

2026-08-05 已对中文与英文 Wikipedia 各做三页实时请求。两边都在一次响应中返回 HTML 导言、分类、`pageprops`、修订 ID 与时间，样本也保留可用于遮蔽的 `<b>` 标记。单请求结构成立，尚未证明的是 20 页批次的延迟和同类四候选成功率。

质量边界：

- MediaWiki 随机模块只随机起点，后续页面顺序固定；页面内可重新安全洗牌，但不能宣传为全站完全独立均匀抽样。
- 20 个随机条目可能跨人物、地点、作品、组织、生物和事件。需按当前响应中的分类做轻量分组，只从同类生成四选一。
- 分类规则须分别适配中英文；不足四个时明确说明本批没有形成题目，由读者主动重试，不自动再请求。
- 通过 `pageprops` 排除消歧义页，同时排除列表、日期、过短导言和名称未充分遮蔽的条目。
- Wikipedia 文本采用 CC BY-SA；揭晓时回链原条目与修订、注明许可和修改。

可以增加“逐句揭示”而不增加网络请求：响应已经包含完整导言，先显示第一句，读者选择作答或继续揭示。该变化能让 Wikipedia 来源和现有萌娘百科四选一产生一点体验差异。

官方证据：

- 随机页面接口：<https://www.mediawiki.org/wiki/API:Random>
- 导言接口与一次最多 20 页：<https://www.mediawiki.org/wiki/Extension:TextExtracts>
- 消歧义标记：<https://www.mediawiki.org/wiki/Extension:Disambiguator>
- 修订 ID：<https://www.mediawiki.org/wiki/API:Revisions/en>
- Wikipedia 文本许可：<https://wikimediafoundation.org/what-we-do/wikimedia-projects/wikipedia/>
- 重用、署名与修改要求：<https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use/en>

## AIC 视觉题在新边界下的状态

AIC 无密钥，能按 `is_public_domain=true` 筛选馆藏，并明确允许 IIIF 图片热链与 CORS。它仍是许可最清楚的视觉来源，但不能再依靠预先生成合格索引。

可接受的原型只能实时完成：玩家点击开始后，请求公共领域绘画的小批元数据，再加载本局实际展示的候选图；响应只留在当前内存。首次随机选择可能需要先取得结果总数，再取随机页；如果一次批次没有足够合格图，应让读者主动重试。必须先验证能否在不续页、不下载 ID 全表的情况下取得足够随机且安全的题目，并把首局与后续局的请求数量写进披露。

由于 AIC 搜索窗口、随机页偏差、四张图片的流量和通用内容过滤都尚未验证，它从并列 P0 降为 P1/P2 原型；不先承诺上线。

官方文档：<https://api.artic.edu/docs/>

## 下一步

只推进 **Wikipedia 来源的实时浏览器原型**：像真实玩家一样逐局点击，中英文先各试玩 20 局，记录响应时间、同类四候选成功率、遮蔽失败率和导言自然度。测试不得循环抓取、保存完整外部条目或形成可发布题池，只保留聚合计数、匿名失败类别和少量必要的来源 ID 作为可复核样本。

只有成功率与请求时延达到可用水平，才进入“百科条目猜猜”来源选择的功能实现；逐句揭示继续留作首版之后的独立增强。AIC、Bangumi 和 AniList 均暂不实现，分别等待实时抽样、接口稳定性和题目质量验证。

当前已将首轮实施边界、Wikipedia 单请求参数、来源选择、匿名化、同类候选、许可披露、测试和发布闸门固化到 `docs/superpowers/plans/2026-08-05-encyclopedia-entry-quiz.md`。计划明确把逐句揭示推迟为后续独立增强；当前尚未开始功能实现或正式发布。
