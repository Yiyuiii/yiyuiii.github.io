# 外部开放数据小游戏调研（2026-08-05）

## 目标

为“小玩意”页寻找能够借用大型外部数据集、同时适合静态双语网站的轻量小游戏。候选必须分别核查数据许可、文本许可、图片许可、浏览器直连、限流、内容过滤、双语覆盖、随机抽样质量和运行时隐私；API 或服务端代码开源不等于其内容与图片可以复用。

现有页面已经有条目导言猜谜、感知、计时、演绎、算术和网格操作。下一款外部数据游戏应优先带来新的循环，而不是换一个百科站再做一次导言四选一。

## 结论

优先保留两条互补路线：

1. **Wikidata 时间线**：从外部大数据集生成可重建、可审计的本地双语题池；玩家把四个人物、作品、发明或事件按时间排序。运行时不联网，是当前风险最低的首选原型。
2. **名画一瞥**：使用 Art Institute of Chicago（AIC）明确标为公共领域的馆藏图和 IIIF 服务；先短暂展示局部，再从若干完整画面中找出来源。题目依靠视觉匹配，不要求中文玩家识别英语馆藏标题，是玩法差异最大的视觉候选。

若希望继续 ACG 路线，Bangumi 的文字条目与角色关系可作为第二阶段来源；封面不进入首版。MusicBrainz、Smithsonian 和 Open Library 作为后续储备。AniList、Europeana 以及未逐图校验许可的 Wikimedia Commons 图片暂不作为首选。

## 数据接入方式

### 1. 构建期生成本地题池（默认方案）

用脚本从开放数据源生成数千条合格记录，保存来源 ID、双语标签、事实、源修订号与许可说明；测试后提交压缩数据，浏览器只在本地题池中使用 `crypto.getRandomValues()` 抽取。

这不是“从全库均匀随机”，页面应如实称为“题目整理自 Wikidata 等开放数据”，并公开题池规模与更新时间。其优势是无运行时第三方请求、无 API 宕机、能提前剔除缺译、歧义、成人和低质量记录，也不会退化为人工维护的小白名单。

### 2. 本地索引 + 点击后请求许可明确的图片

本地索引只保存合格记录、图片 ID 和许可证据；用户明确点击开始后才请求外部图片。入口必须说明第三方会看到请求、来源页和 IP 地址。图像服务失败时保留重试或换题，不自动连续请求。

### 3. 每局实时请求 API

仅在服务提供稳定 CORS、无需暴露密钥、单局请求有明确上限且响应能在浏览器本地可靠筛选时使用。实时“随机”仍需证明候选分布与质量，不能把 API 返回的第一页或随机 ID 猜测当成均匀抽样。

### 为什么首选 Wikidata 时间线

Wikidata 当前有超过 1.2 亿个 Item 和 130 万个 Lexeme，结构化数据以 CC0 提供，并有中英文标签。官方也明确提醒：WDQS 适合范围明确的查询，不适合大结果集；Action API 适合小批量直接读取实体。因此正式方案不在玩家每局开始时向 WDQS 做昂贵随机查询，而是在构建期生成题池。

首版题池建议：

- 四类主题：人物出生、作品首发、发明/发现、历史事件；默认混合，可折叠选择主题；
- 每条必须同时有中文和英文标签、一个可比较的明确日期、来源 QID 与修订信息；
- 使用 sitelink 数量等可复核信号剔除过于冷门的记录，但不宣称它等同“知名度”；
- 同一题的四个选项来自同类主题，日期不得相同，歧义日期和约数日期不进入首版；
- 首批目标是数千条实体记录，由记录动态组合大量题目；不宣传成“在 1.2 亿条中均匀随机”；
- 作答后显示正确顺序、年份与各自的 Wikidata 来源链接；本地数据不要求署名，但仍主动注明来源；
- 随机抽取用既有安全随机接口，避免近期重复，不保存历史。

原型闸门：自动校验全部字段和日期；随机生成至少 10 万题检查无重复选项、无相同日期、主题一致；人工审阅 100 题检查翻译自然、实体可辨和难度分布。

### 为什么 AIC 比 Met 更适合先做视觉原型

Met 的 CC0 数据和公共领域图规模更大，API 也无需密钥；但常见流程先取得对象 ID，再逐个请求详情。AIC 的搜索字段、公共领域过滤、IIIF 裁切、CORS 和热链说明更完整，能用更少的工程假设验证视觉玩法。AIC 仍需先建立合格索引，不能每局临时从搜索结果碰运气。

“名画一瞥”建议避开馆藏标题翻译问题：

1. 点击开始后，短暂显示一块有辨识度的画面局部；
2. 局部隐藏，显示三至四张完整作品缩略图；
3. 玩家找出局部来自哪一幅；
4. 揭晓后才显示馆藏原题名、作者、年代、来源和公共领域说明。

首版可限定为风景、静物和植物等较容易做通用内容过滤的绘画，不把全部馆藏直接暴露给随机抽样。索引需逐条满足：`is_public_domain=true`、存在 `image_id`、图片可用、尺寸足够、类别合格；再对局部可辨识度、极端长宽比、近重复作品和敏感内容做抽样审计。默认只在点击开始后请求图片；若一局需要多张候选图，入口如实说明请求数量和隐私边界。

### Bangumi 的可行边界

Bangumi 官方版权页称条目信息（含封面、介绍、章节）与角色信息由用户提供、遵循 CC BY-SA，同时说明已有版权作品按 fair use 并标来源。因为封面可能来自受版权保护作品，首版只用结构化文字、日期和关系，不把“API 返回了图片”视为图片授权。

2026-08-05 的最小实测中，`GET https://api.bgm.tv/v0/subjects?type=2&limit=1` 匿名返回 `200`，并返回 `Access-Control-Allow-Origin: *`。一次随后读取正文的测试在 30 秒内未完成，因此正式实现仍须做多时段延迟与失败率实测。每道题需提供 Bangumi 来源链接、CC BY-SA 署名说明，过滤成人/敏感内容，并复核分享相同方式的适用范围。

更合适的循环不是再猜导言，而是：

- 给出一部作品与四个角色，找出并不属于它的一个；
- 给出一组“原作—动画—续作”关系，选出正确关系；
- 将四部作品按首播/首发时间排序。

其中“找出不属于作品的角色”最直观，但与现有萌娘百科题材接近，排在视觉和通用知识题之后。

## 暂不优先的看似诱人方案

- **维基百科导言猜猜**：数据量大且接口成熟，但核心循环几乎复制萌娘百科条目猜猜，新增价值低。
- **动画封面或角色图猜猜**：Bangumi/AniList 能返回图片地址，不代表这些图片具有可复用许可；在逐图权利证据建立前不做。
- **听歌猜曲**：MusicBrainz 提供的是元数据，不提供歌曲版权；不用未经授权的音频预览。
- **随便抽 Wikimedia Commons 图片**：Wikidata 数据 CC0 不会自动覆盖 `P18` 指向文件的许可；必须逐文件读取并保留许可、作者和署名要求，工程量高于 AIC 单馆公共领域方案。
- **OpenStreetMap 街景猜地点**：OSM 是地图数据，不提供街景；瓦片服务有独立使用政策，若接第三方街景又会增加许可、密钥和追踪问题。
- **国旗猜国家**：可本地实现且双语简单，但题量有限、玩法常见，不能充分利用外部大数据集；旗帜和徽章的权利也需按国家逐项判断。

## 下一步

先做 **Wikidata 时间线**的数据可行性原型，不进入页面代码：编写可重生成脚本、生成一批约 300 条的中英双语样本、运行日期与组合属性测试，再把 100 道最小审阅样本整理成单页 HTML 供人工试玩。只有样本的自然度和可玩性通过后，才扩大题池并实现正式交互。

AIC 同时只做独立的 100 件公共领域绘画审计，验证局部裁切、候选相似度、内容安全、图片请求数和加载体验；不在双语标题映射未解决时承诺正式上线。
