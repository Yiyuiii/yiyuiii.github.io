# 外部开放数据小游戏调研（2026-08-05）

## 目标

为“小玩意”页寻找能够借用大型外部数据集、同时适合静态双语网站的轻量小游戏。候选必须分别核查数据许可、文本许可、图片许可、浏览器直连、限流、内容过滤、双语覆盖、随机抽样质量和运行时隐私；API 或服务端代码开源不等于其内容与图片可以复用。

用户进一步明确：**不做任何需要 API 密钥的项目**。站点、维护者和读者都不应申请或提供密钥；不得把密钥嵌入静态前端，也不为小游戏新增代签后端。公开数据导出若本身无需密钥，仍可用于构建本地题池。

现有页面已经有条目导言猜谜、感知、计时、演绎、算术和网格操作。下一款外部数据游戏应优先带来新的循环，而不是换一个百科站再做一次导言四选一。

## 结论

优先保留两条互补路线：

1. **Wikidata 时间线**：从外部大数据集生成可重建、可审计的本地双语题池；玩家把四个人物、作品、发明或事件按时间排序。运行时不联网，是当前风险最低的首选原型。
2. **名画一瞥**：使用 Art Institute of Chicago（AIC）明确标为公共领域的馆藏图和 IIIF 服务；先短暂展示局部，再从若干完整画面中找出来源。题目依靠视觉匹配，不要求中文玩家识别英语馆藏标题，是玩法差异最大的视觉候选。

若希望继续 ACG 路线，Bangumi 的文字条目与角色关系可作为第二阶段来源；封面不进入首版。MusicBrainz 和 Open Library 只作为无需密钥的元数据储备。AniList、未逐图校验许可的 Wikimedia Commons 图片暂不作为首选；Europeana 等必须使用密钥的路线从候选中删除。

## 数据接入方式

### 1. 构建期生成本地题池（默认方案）

用脚本从开放数据源生成数千条合格记录，保存来源 ID、双语标签、事实、源修订号与许可说明；测试后提交压缩数据，浏览器只在本地题池中使用 `crypto.getRandomValues()` 抽取。

这不是“从全库均匀随机”，页面应如实称为“题目整理自 Wikidata 等开放数据”，并公开题池规模与更新时间。其优势是无运行时第三方请求、无 API 宕机、能提前剔除缺译、歧义、成人和低质量记录，也不会退化为人工维护的小白名单。

### 2. 本地索引 + 点击后请求许可明确的图片

本地索引只保存合格记录、图片 ID 和许可证据；用户明确点击开始后才请求外部图片。入口必须说明第三方会看到请求、来源页和 IP 地址。图像服务失败时保留重试或换题，不自动连续请求。

### 3. 每局实时请求 API

仅在服务提供稳定 CORS、无需暴露密钥、单局请求有明确上限且响应能在浏览器本地可靠筛选时使用。实时“随机”仍需证明候选分布与质量，不能把 API 返回的第一页或随机 ID 猜测当成均匀抽样。

### 为什么首选 Wikidata 时间线

Wikidata 当前有超过 1.2 亿个 Item 和 130 万个 Lexeme，结构化数据以 CC0 提供，并有中英文标签。官方也明确提醒：WDQS 适合范围明确的查询，不适合大结果集；Action API 适合小批量直接读取实体。因此正式方案不在玩家每局开始时向 WDQS 做昂贵随机查询，而是在构建期生成题池。

首版题池建议：

- 四类主题：人物出生、作品首发、发明/发现、历史事件；默认混合，可折叠选择主题；
- 每条必须同时有中文和英文标签、一个可比较的明确日期、来源 QID 与修订信息；
- 使用 sitelink 数量等可复核信号剔除过于冷门的记录，但不宣称它等同“知名度”；
- 同一题的四个选项来自同类主题，日期不得相同，歧义日期和约数日期不进入首版；
- 首批目标是数千条实体记录，由记录动态组合大量题目；不宣传成“在 1.2 亿条中均匀随机”；
- 作答后显示正确顺序、年份与各自的 Wikidata 来源链接；本地数据不要求署名，但仍主动注明来源；
- 随机抽取用既有安全随机接口，避免近期重复，不保存历史。

原型闸门：自动校验全部字段和日期；随机生成至少 10 万题检查无重复选项、无相同日期、主题一致；人工审阅 100 题检查翻译自然、实体可辨和难度分布。

### 为什么 AIC 比 Met 更适合先做视觉原型

Met 的 CC0 数据和公共领域图规模更大，API 也无需密钥；但常见流程先取得对象 ID，再逐个请求详情。AIC 的搜索字段、公共领域过滤、IIIF 裁切、CORS 和热链说明更完整，能用更少的工程假设验证视觉玩法。AIC 仍需先建立合格索引，不能每局临时从搜索结果碰运气。

“名画一瞥”建议避开馆藏标题翻译问题：

1. 点击开始后，短暂显示一块有辨识度的画面局部；
2. 局部隐藏，显示三至四张完整作品缩略图；
3. 玩家找出局部来自哪一幅；
4. 揭晓后才显示馆藏原题名、作者、年代、来源和公共领域说明。

首版可限定为风景、静物和植物等较容易做通用内容过滤的绘画，不把全部馆藏直接暴露给随机抽样。索引需逐条满足：`is_public_domain=true`、存在 `image_id`、图片可用、尺寸足够、类别合格；再对局部可辨识度、极端长宽比、近重复作品和敏感内容做抽样审计。默认只在点击开始后请求图片；若一局需要多张候选图，入口如实说明请求数量和隐私边界。

### Bangumi 的可行边界

Bangumi 官方版权页称条目信息（含封面、介绍、章节）与角色信息由用户提供、遵循 CC BY-SA，同时说明已有版权作品按 fair use 并标来源。因为封面可能来自受版权保护作品，首版只用结构化文字、日期和关系，不把“API 返回了图片”视为图片授权。

2026-08-05 的最小实测中，`GET https://api.bgm.tv/v0/subjects?type=2&limit=1` 匿名返回 `200`，并返回 `Access-Control-Allow-Origin: *`。一次随后读取正文的测试在 30 秒内未完成，因此正式实现仍须做多时段延迟与失败率实测。每道题需提供 Bangumi 来源链接、CC BY-SA 署名说明，过滤成人/敏感内容，并复核分享相同方式的适用范围。

更合适的循环不是再猜导言，而是：

- 给出一部作品与四个角色，找出并不属于它的一个；
- 给出一组“原作—动画—续作”关系，选出正确关系；
- 将四部作品按首播/首发时间排序。

其中“找出不属于作品的角色”最直观，但与现有萌娘百科题材接近，排在视觉和通用知识题之后。

## 四个方向详解

### AniList

AniList 的公开 GraphQL 查询确实**不需要密钥或登录**。官方文档允许未认证客户端查询动画、漫画和角色，能一次取得标题、简介、播出日期、原作类型、制作公司、角色关系、流行度、成人标记、封面 URL 和站内链接。

它适合的文字游戏包括：

- 给出动画与四个角色，找出不属于该作品的一位；
- 给出原作类型、年代、集数和制作公司，猜作品；
- 从四部动画中找出最早播出或唯一不同原作类型的一部；
- 给出续作、前传、外传关系，选出正确关系链。

但正式接入有四个结构性问题：

1. **不可建立大型本地镜像**：官方条款禁止把 API 当备份/数据存储，也禁止 hoarding 或 mass collection。本站偏好的“构建期生成数千条题池”与这条存在冲突，因此只能小批量实时读取，不能把 AniList 全库抓成本地数据。
2. **当前稳定性不足**：正常说明为每分钟 90 次，但官方当前明确标为降级状态、限为每分钟 30 次；严重故障时还可能直接暂停 API。一个轻量客户端单人不会撞限流，但游戏能否开始受第三方实时状态控制。
3. **没有中文题名通道**：`MediaTitle` 只有罗马字、英语、原生语言和用户偏好字段；未登录时用户偏好默认罗马字。原生题名可能是日语、韩语或中文，不能等同中文本地化。若另接 Bangumi 映射中文名，又引入跨库实体匹配、许可和第二次请求。
4. **封面许可没有随 API 字段给出**：官方参考只说明 `coverImage` 返回若干尺寸的 URL，没有为每张封面提供可复用许可证。API 使用许可不能替代原作品或宣传图版权许可。

此外，`isAdult=false` 也不是完整的通用内容过滤。AniList 官方明确提醒其成人过滤不保证符合其它平台标准，且 Ecchi 不被归为成人。正式题目仍需额外排除敏感标签与可能含剧透的标签。

因此 AniList 的结论是：**技术上符合无密钥要求，但只适合一次请求一局、文字与关系为主的小原型；不适合本地大题库，也不为动画封面猜题提供足够的权利证据。** 当前排序低于 Bangumi 文字关系题。

- API 使用条款与禁止批量囤积：<https://docs.anilist.co/guide/terms-of-use>
- 当前降级限流：<https://docs.anilist.co/guide/rate-limiting>

### 动画封面猜题

最自然的循环是显示一张被裁切、模糊或逐步揭开的封面，再从四个标题中找答案。它视觉直接、重玩性高，也能明显区别于萌娘百科导言题；但目前不进入实现，原因不在技术，而在图片权利。

- Bangumi 官方版权页一方面把封面列入用户提供的条目信息，另一方面明确说已有版权作品按 fair use 处理并标来源。Bangumi 能在自身语境展示封面，不等于本站取得了再利用或裁切封面的许可。
- AniList 只返回封面 URL，不提供逐图许可证，也没有在已核查的 API 条款中授权把封面用于独立猜谜娱乐。
- “热链”只描述文件从哪里加载，不会改变版权；“缩小、裁切、模糊”仍然是在利用原图，也不能自动消除权利问题。
- 封面常直接包含作品标题；同一系列不同季度、总集篇、剧场版和重制版又高度相似。即使许可解决，仍需 OCR/文字泄漏检测、系列去重、成人内容过滤和相似候选生成。

若未来得到明确许可，较好的机制应是：

1. 只在点击开始后加载一张封面，披露第三方请求和 IP；
2. 首先显示不含大块文字的局部，错误后逐步扩大范围；
3. 四个候选来自相近年代、类型和热度，并排除同一系列，避免答案过于明显或语义争议；
4. 中文页必须有可靠中文名，英文页用官方英文名或罗马字；
5. 揭晓时给出作品页、图片来源和逐图许可。

当前结论：**不做**。只有出现无需密钥、逐图明确允许第三方展示与改编、又能稳定提供中英题名的数据源时再重启。

### 听歌猜曲

主流玩法是播放 5–15 秒片段，让玩家从标题或歌手中选择。元数据并不是最大问题，真正的阻碍是录音权：作曲、歌词、表演和具体录音可能分别受保护。

- MusicBrainz 无需密钥，核心元数据大多为 CC0，但官方明确说明它不存储也无法访问音乐录音；它只能提供曲名、艺人、发行和关系数据。
- Apple iTunes Search API 虽然无需项目密钥并返回歌曲预览，但官方条款只允许这些预览用于推广对应商店内容，要求商店徽章、购买链接与署名，并明确禁止把预览用于脱离推广目的的独立娱乐。因此不能拿来做本站猜歌游戏。
- Spotify、Jamendo、Freesound 等常见路线需要应用凭据或密钥，按用户要求直接排除。
- Wikimedia Commons 无需密钥并只接受自由许可或公共领域音频，但每个文件都有自己的许可证、作者、表演者与录音权说明，必须逐文件保存证据；它更适合经过审计的“听声猜物”“猜乐器/动物/环境”，而不是主流流行歌曲竞猜。

如果仍要保留声音游戏，建议改成 **“听声猜猜”**：从 Wikimedia Commons 构建一个许可可审计的本地索引，主题限定为乐器、动物、环境和公共领域录音；每题播放短片段，提供文字按钮，揭晓时展示来源、作者和许可。正式前还要验证音频体积、跨域分段加载、无声环境提示和听障用户的替代说明。若要把片段下载、裁剪并同源托管，必须逐条确认许可证允许修改，并保留修改说明与署名。

当前结论：**不做主流“听歌猜曲”；可以把“听声猜猜”列入较后研究池。**

- MusicBrainz 数据许可：<https://musicbrainz.org/doc/About/Data_License>
- iTunes 预览只能用于推广：<https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/>
- Commons 音频及录音权要求：<https://commons.wikimedia.org/wiki/Commons:Audio/en>

### 新的百科导言猜题

最现实的数据源是中文维基百科与英语维基百科。两者使用同一套无密钥 MediaWiki API，中英文页面可以请求各自语种，不再出现英语界面只能显示中文题料的问题。Wikipedia 文本可按 CC BY-SA 重用，但每题必须在揭晓时回链原条目、注明许可和“名称已遮蔽”等修改。

建议不要增加一个几乎相同的新折叠项，而是把现有游戏扩展为 **“百科条目猜猜”**，在开始前选择来源：

- 中文页：保留萌娘百科为默认来源，可选中文维基百科；
- 英文页：默认 English Wikipedia，可选明确标注为中文题料的 Moegirl；
- 来源、语种、请求次数、许可和隐私说明随选择同步变化。

维基百科路线可以保持一次请求一局：用 `generator=random` 限定主命名空间，取最多 20 个随机页面，同时请求导言 HTML、分类、消歧义标记与修订 ID。导言的 `<b>` 片段通常包含条目名和别名，可先统一替换为遮蔽块，再转成纯文字；这比只按标题字符串替换更能消除别名泄漏。作答后链接到该修订版本，并显示 CC BY-SA 说明。

2026-08-05 对中文与英文 Wikipedia 各做了一次三页实时请求：两边都能在同一响应中返回 HTML 导言、分类、`pageprops`、修订 ID 与时间；样本导言也保留了可用于遮蔽名称的 `<b>` 标记。该实测证明单请求结构成立，但不代表 20 页批次的延迟和合格题率已经达标。

真正困难的是候选质量：

- MediaWiki 的随机模块只随机起点，后续页面顺序固定；页面内应重新安全洗牌，但不能宣称每个题目组合都从全站独立均匀抽取。
- 20 个随机条目可能同时包含人物、地点、化学物、组织和事件。若直接选四个，会因类别差异过大而过于简单。
- 分类体系在中文和英文中不同，需分别建立轻量分类器，把候选先分成人物、地点、作品、组织、生物、事件等，再从同类生成四选一；不足四个时明确提示重试，不偷偷继续请求。
- 消歧义页可通过 `pageprops` 排除；列表、日期、过短导言、标题或别名无法充分遮蔽的条目也要排除。
- TextExtracts 一次最多返回 20 个导言，因此不能像萌娘百科先随机 50 页再为全部附加导言；这是一轮题目质量的实际上限。

它还可以用“逐句揭示”稍微区别于现有玩法：先显示第一句，玩家可以作答或再揭示一句；揭示越少不必评分，只作为个人挑战。这比另造一套积分更符合随开随走的定位。

当前结论：**四项里最值得继续**。但更适合成为现有条目猜猜的多来源升级，而不是新增一款同构游戏。先对中英文各抽样 200 批，统计同类四候选成功率、遮蔽失败率和导言自然度，再决定是否实现。

## 暂不优先的看似诱人方案

- **把维基百科导言猜猜做成独立新游戏**：数据量与接口都合格，但会复制现有循环；只考虑把它作为现有“百科条目猜猜”的可选来源和双语升级。
- **动画封面或角色图猜猜**：Bangumi/AniList 能返回图片地址，不代表这些图片具有可复用许可；在逐图权利证据建立前不做。
- **听歌猜曲**：MusicBrainz 提供的是元数据，不提供歌曲版权；不用未经授权的音频预览。
- **随便抽 Wikimedia Commons 图片**：Wikidata 数据 CC0 不会自动覆盖 `P18` 指向文件的许可；必须逐文件读取并保留许可、作者和署名要求，工程量高于 AIC 单馆公共领域方案。
- **OpenStreetMap 街景猜地点**：OSM 是地图数据，不提供街景；瓦片服务有独立使用政策，若接第三方街景又会增加许可、密钥和追踪问题。
- **国旗猜国家**：可本地实现且双语简单，但题量有限、玩法常见，不能充分利用外部大数据集；旗帜和徽章的权利也需按国家逐项判断。

## 下一步

先做 **Wikidata 时间线**的数据可行性原型，不进入页面代码：编写可重生成脚本、生成一批约 300 条的中英双语样本、运行日期与组合属性测试，再把 100 道最小审阅样本整理成单页 HTML 供人工试玩。只有样本的自然度和可玩性通过后，才扩大题池并实现正式交互。

AIC 同时只做独立的 100 件公共领域绘画审计，验证局部裁切、候选相似度、内容安全、图片请求数和加载体验；不在双语标题映射未解决时承诺正式上线。
