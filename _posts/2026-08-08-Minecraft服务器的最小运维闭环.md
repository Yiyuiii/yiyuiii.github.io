## 为什么“能运行”还不够 {#why-running-is-not-enough}

第一次把服务器启动起来，通常只需下载文件、安装 Java、接受许可并执行命令。真正消耗精力的是几周之后：模组要求另一版 Java，磁盘悄悄写满，更新后世界打不开，进程退出却没人发现，或者备份从未做过恢复测试。

因此，我现在把“服务器已经搭好”定义为一个闭环，而不是一次成功启动：

1. 能明确复现当前版本和依赖；
2. 进程在受控身份下启动、停止和失败重启；
3. 网络只暴露必要入口；
4. 世界、配置和模组有可验证备份；
5. 更新先在副本上演练，失败时能回滚；
6. 日志、磁盘和存活状态有人看得见。

这篇文章针对朋友间的小型 Minecraft Java Edition 服务器。它不是面向大规模公共服的高可用架构，也不会公开我的端口、玩家 UUID、账户或实际目录。

## 先冻结一张兼容性卡片 {#freeze-a-compatibility-card}

不要从“机器上最新的 Java”反推服务器应该能运行。先正向记录四个彼此约束的版本：

| 层 | 要记录什么 | 为什么重要 |
|---|---|---|
| 游戏 | Minecraft 精确版本 | 世界格式、协议和模组都依赖它 |
| 服务端 | Vanilla、Forge、Fabric 等及其构建号 | 启动方式与兼容范围不同 |
| 运行时 | Java 主版本与发行版 | 过新和过旧都可能不兼容 |
| 内容 | 模组、数据包与配置的版本清单 | 仅有服务端 JAR 无法复现世界行为 |

例如，[Forge 1.20.1 的官方入门文档](https://docs.minecraftforge.net/en/1.20.1/gettingstarted/)明确以 64 位 Java 17 JDK 为前提。这个事实比“我电脑上的 Java 版本更高”更有约束力。原版服务端则应从[Minecraft 官方服务器页面](https://www.minecraft.net/en-us/download/server)取得，并遵守[Minecraft EULA](https://www.minecraft.net/en-us/eula)。

我会把这张卡片与服务端文件放在一起，并额外保存文件哈希。升级时新建一张，不覆盖旧卡片；这样回滚面对的是一组完整版本，而不是一个来历不明的 JAR。

## 用专用身份和监督器启动 {#run-under-a-dedicated-identity}

服务端不需要管理员权限。给它一个不能交互登录的专用系统账户，只允许读写自己的服务目录；下载、上传和修改文件则由维护流程显式完成。这样即使模组或插件有漏洞，能够触碰的范围也更小。

启动脚本也不应该用无限 `while true` 把所有退出都当成正常重启。监督器能够区分人工停止与异常退出，限制重启频率，并把日志交给统一系统。下面是一份刻意保留占位符的 `systemd` 骨架：

```ini
[Unit]
Description=Minecraft Java server
After=network-online.target

[Service]
User=minecraft
WorkingDirectory=/srv/minecraft/current
ExecStart=/usr/bin/java -Xms2G -Xmx4G -jar server.jar nogui
Restart=on-failure
RestartSec=10
SuccessExitStatus=0 143

[Install]
WantedBy=multi-user.target
```

内存数值、文件名和目录只是示意，必须按机器与服务端实现调整。初次启动后，应阅读许可文本，再由维护者明确接受，而不是从陌生教程复制一个已经设好的 `eula=true`。

## 只开放必须开放的入口 {#expose-only-what-is-required}

“进程在监听”不等于“应该让整个互联网访问”。先决定服务器只供本地网络、虚拟专网、固定来源还是公开玩家使用，再配置对应的防火墙和路由。Ubuntu 当前的[防火墙文档](https://documentation.ubuntu.com/server/how-to/security/firewalls/)以 `ufw` 作为常见前端；我的原则是默认拒绝入站，只允许实际使用的服务入口，并保留可审查的规则和日志。

运维入口与游戏入口要分开考虑。远程管理优先使用密钥认证、限制来源并关闭不需要的账户；不要把管理面板、远程终端和游戏端口一起暴露，也不要把密钥、玩家权限文件或公网地址写进公开文章和代码仓库。

## 把配置当成可审阅差异 {#treat-configuration-as-reviewable-diffs}

`server.properties`、白名单、权限、模组配置和启动参数共同决定服务器行为。复制整份配置很快，却会把默认值、私人标识和过期选项混在一起。我更愿意保留三样东西：

- 一份从干净默认配置到当前配置的最小差异；
- 一份不含秘密信息的版本说明；
- 一份部署后人工验收清单。

每次只改一组有明确目的的选项，启动后从服务端日志确认配置被识别，再由普通玩家账户完成连接、出生点、权限和关键模组的短验收。管理员权限文件中的 UUID 和用户名属于私人运行数据，不进入教程。

## 备份必须包含一次恢复 {#a-backup-must-include-a-restore}

只看见压缩包并不能证明备份可用。一个小服的最低闭环可以是：

1. 在一致状态下保存世界；最稳妥的是有计划地停止服务，在线快照则必须遵循服务端支持的保存流程；
2. 同时保存世界目录、服务端配置、模组及兼容性卡片；
3. 计算校验和，并把至少一份副本放到故障域之外；
4. 在隔离目录解压，用同一兼容性卡片启动；
5. 实际进入世界，检查出生、区块、背包、权限和关键模组；
6. 记录恢复日期、耗时和发现的问题。

保留策略应覆盖“刚刚误删”“几天后才发现损坏”和“整台主机丢失”三种时间尺度。备份过程本身也要监控：磁盘满时生成的零字节归档，比没有备份更容易造成错觉。

## 更新是一场可回滚的演练 {#make-updates-rehearsable}

我不会在唯一的世界副本上直接替换服务端。更新顺序固定为：

1. 阅读游戏、加载器和模组的发行说明，重新填写兼容性卡片；
2. 创建并验证更新前备份；
3. 在隔离副本中安装新版本，保留旧目录只读；
4. 启动并扫描错误、缺失模组、数据迁移与弃用警告；
5. 用普通账户完成短验收，并测试停止与再次启动；
6. 设定维护窗口后切换；异常就停服并恢复旧版本与旧世界，不能把新版本写过的世界随意交回旧服务端。

回滚条件应在更新前写下，例如无法启动、关键模组失效、世界加载错误或延迟超过可接受范围。否则维护者很容易在故障现场不断叠加“再试一个修复”，最终失去清晰的恢复点。

## 监控少而关键的信号 {#monitor-a-small-set-of-signals}

朋友服不需要复杂监控平台，但至少要回答：进程是否存活、最近一次备份是否成功、磁盘还剩多少、日志是否连续出现异常、玩家是否能完成一次真实连接。

我把检查分成两层：

- **机器信号**：服务状态、退出码、CPU、内存、磁盘、备份年龄和日志错误；
- **玩家信号**：连接、进入世界、移动到已知区块、执行普通指令、退出后数据仍能保存。

机器信号适合自动告警，玩家信号适合更新后的短验收。两者缺一不可：进程绿色并不代表世界可玩，玩家偶尔能进也不代表备份和磁盘健康。

## 一页维护清单 {#one-page-maintenance-checklist}

**首次上线**

- [ ] 游戏、服务端、Java 与内容版本已记录；
- [ ] 许可由维护者明确接受；
- [ ] 使用专用低权限账户和受控服务；
- [ ] 防火墙只开放预期入口；
- [ ] 私人标识与凭据没有进入公开仓库；
- [ ] 已完成一次备份和隔离恢复；
- [ ] 普通玩家账户已通过短验收。

**每次更新**

- [ ] 新兼容性卡片和回滚条件已写下；
- [ ] 更新前备份已经实际恢复验证；
- [ ] 新版本先在副本上启动；
- [ ] 日志、权限、关键模组和世界数据已检查；
- [ ] 切换后仍保留可定位的旧版本与恢复记录。

这套流程没有追求“大服架构”。它只把一次性的安装命令，变成一台小服务器能够长期解释、维护和恢复的最小系统。
